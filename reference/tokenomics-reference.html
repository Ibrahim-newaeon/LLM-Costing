Three corrections to your sourcing plan

Two of them change the architecture

Your hybrid sourcing strategy is the right shape — local tokenizers for speed, aggregator feeds for prices, manual overrides for enterprise and Chinese clouds. Three specifics need verifying before you commit, because "zero network latency" doesn't hold for all of them.

⚠️ Verify 1 — Anthropic has no public local tokenizer

Claude token counting is a network API call (POST /v1/messages/count_tokens), not a local library. There is no published Claude tokenizer to load the way you load tiktoken. Treating it as local will silently break the latency and rate-limit budget for every Claude estimate.

→ Architect as a remote, rate-limited adapter cached by content hash, with a CALIBRATED_HEURISTIC fallback tagged MEDIUM confidence for offline/preview mode.
⚠️ Verify 2 — Gemini countTokens is primarily remote

The Generative AI SDK's countTokens is an API call. A local text-token path does exist via the Vertex AI SDK, but confirm current coverage — particularly whether it handles multimodal inputs or text only — before you rely on it.

→ Treat local-Gemini as an optimization, not the default. Ship the remote adapter first.
⚠️ Verify 3 — Chinese closed tiers may publish no tokenizer

Open-weight Qwen, GLM and DeepSeek tokenizers are downloadable from Hugging Face or ModelScope. Baidu ERNIE and Tencent Hunyuan hosted tiers may not ship matching tokenizer files. A nearest-architecture substitute is a proxy, and must say so.

→ Mark the model tokenizer_availability: PROXY, force Low confidence, and surface a PROXY_TOKENIZER_IN_USE warning on the estimate.

The defaults engine, and the line it must not cross

Your instinct is right — refusing to estimate without pixel dimensions makes the product useless. But it collides with the refuse-don't-guess rule. One clean line resolves it:

Guess quantities. Never guess rates.

Three problems with the Chinese multiplier

  • Multiplier relative to what? 1.5–2.5× has no stated baseline. Written properly it's tokens ≈ chars × ratio[model, script] — one measured ratio per pair, never a multiplier on an unnamed English assumption.
  • That band is a ±25% cost swing before anything else varies. It isn't a range you pick from — it's a distribution. Emit P50 and P90 or the user reads the low end as the price.
  • You will almost never need it. Qwen, GLM, DeepSeek and the OpenAI families all have local exact tokenizers. Ratios are for PROXY tokenizers, offline preview and pre-upload estimates only. Applying one when an exact count is available is a self-inflicted error.

And Arabic is missing from your spec entirely

It needs its own measured ratio plus three rules the Chinese path doesn't have:

  • Tashkeel is billable. Fully vocalized text — Qur'anic, liturgical, formal legal — carries a diacritic on nearly every consonant, and most tokenizers count them. Detect diacritic density and branch; one Arabic ratio for both is wrong.
  • Morphology, not spaces. Arabic packs article, conjunction, preposition and pronoun into one orthographic word. Calibrate on characters, per model — word-based ratios behave much worse.
  • Dialect ≠ MSA. Gulf and Levantine content tokenizes worse on MSA-weighted models. If your Jordan/KSA/Kuwait workloads include chat or social, that's a separate bucket from contracts.

Corpus buckets become en, ar_msa, ar_dialect, ar_vocalized, zh_hans, zh_hant, code, json, mixed — each with its own sample count, mean, p90 and stddev.

Three corrections to the tier spec

⚠️ The ~3.5–4 chars/token figure is English prose only

Applying it to Arabic or Chinese is confident, silent, and wrong by a large factor — exactly the failure the whole section exists to prevent. No bootstrap constant for those scripts appears anywhere in this spec, and inventing one is forbidden.

→ Tier 3 returns UNAVAILABLE for an uncalibrated script and the UI shows a live character count. A blank token field is honest; a wrong one isn't.
⚠️ The +15% safety pad is directional — it needs two numbers, not one

Overflow checks want to over-estimate so a wrong guess fails safe. A cost quote wants to be centred, because padding inflates what you tell the client. One padded number serving both means you either overquote or overflow.

→ cost_estimate (raw, feeds pricing) and context_safety_estimate (padded, feeds limit checks) stay separate all the way to the UI. Padding never touches a price, and never applies above Tier 3.
⚠️ A proxy must match the script, not just the architecture

"Map to a LLaMA/Qwen baseline" treats those as interchangeable. For Chinese they aren't — a Chinese-native vocabulary and an older Western-trained one fragment Hanzi very differently. Proxying a Chinese closed tier to a Western tokenizer is wrong in a consistent direction, which makes it look stable and keeps it from being noticed.

→ Chinese models proxy to Chinese-native open tokenizers. Record basis and measured_delta_pct; a null delta forces LOW confidence, and exceeding PROXY_DRIFT_MAX_PCT disables the proxy entirely.

Two additions worth wiring on day one

  • Every Tier 1 call is a free calibration sample. When the remote count returns, compute what Tiers 2 and 3 would have said and store the deltas. The heuristic improves as a by-product of normal operation, and proxy drift surfaces as a widening delta before it becomes a wrong invoice. Retrofitting this means discarding every sample you already paid for.
  • Gemini's local path must detect media and refuse. Multimodal weight depends on resolution downscaling and frame sampling that the local path doesn't replicate — a counter that quietly counts only the text produces a large, confident undercount. Local Gemini is a text-only optimization; media always escalates.
The invariant that holds all four tiers together 
The `method` and `confidence` on a returned line describe the tier that
ACTUALLY produced the number — never the tier that was requested.

On a 429, a timeout, or an offline fallback: drop one tier, RE-TAG the line,
raise ESCALATION_FAILED. Never present a fallback number wearing the
confidence of the tier you wanted.

A silent downgrade is the same class of bug as a hardcoded rate.

Two rules the evidence hardened

Confidence propagates by minimum — it is computed, never typed

line = min(quantity, rate) → task = min over lines → estimate = min over tasks. A HIGH token count multiplied by an UNAVAILABLE rate is not a HIGH estimate. It isn't an estimate at all.

An aggregator rate may never validate at HIGH

Enforced as a schema refinement, not a code convention — unrepresentable rather than merely documented. This is empirical: on one verification pass against vendor pages, roughly one aggregator rate in three was wrong. Several stale by a price change; one off by 5×.

When documentation runs out, measure

Four quantities have no documentary source anywhere: chat-template framing overhead, per-script token ratios, real throughput, and — newly — vision geometry for the providers that publish rates without a formula. The geometry probe closes the last one: one call per probe point, minus a text-only baseline, gives the visual-token count directly.

Two rules make it trustworthy. Run a control model whose geometry is already published, and refuse to trust the run if the harness can't recover it — a mis-subtracted baseline or a silently ignored detail flag produces plausible numbers and a wrong formula. And never return a best guess: a candidate explaining most points is a coincidence with counterexamples, so anything short of a zero residual on every observation comes back UNKNOWN with the misses listed.

The decisive measurement is a transposed pair. Patch grids, tile grids, area budgets and flat rates are all commutative, so w×h and h×w agree; a width-dependent term does not. One pair of calls halves the candidate set.

The blueprint

Two cost formulas, one honesty contract

Costing split: managed API vs self-hosted

The deployment choice doesn't change the number — it changes the unit. Managed API is per token. Self-hosted is per second of GPU wall-clock, whether or not it is doing anything.

API-managed cost 
API_COST =
    (billable_input  × input_rate(tier))
  + (billable_output × output_rate)
      // billable_output INCLUDES reasoning tokens
  + (image_tokens    × tile_or_image_rate)
  + (audio_seconds   × audio_rate)
  − (cached_tokens   × (input_rate − cache_read_rate))
  + (cache_write     × cache_write_rate)
  + per_request_fees
Self-hosted compute cost 
request_seconds = ttft
  + input_tokens  / prefill_tps
  + output_tokens / decode_tps

effective_seconds =
  request_seconds / concurrency_factor

SELF_HOSTED_COST = effective_seconds
  × (hourly_rate / 3600)
  × (1 + regional_tax)
  ÷ utilization_factor

The gate that runs first. Before either formula, feasibility: weights_bytes + kv_cache_bytes + activation_overhead ≤ gpu_count × vram_per_gpu × usable_fraction. If a model-architecture field is missing from the model card, the answer is UNAVAILABLE — not an estimate.

The number that decides it. Utilization, not hardware. A GPU billed around the clock at low utilization loses to any API. The breakeven-volume chart — where self-hosted crosses below managed API as requests/day rises — is the single most valuable screen in the product, and the prompt says to build it first.

Oversized assets — the disposition ladder

The pre-flight calculator detects a violation; this is what happens next. Constraints are per-model DB fields, never literals.

⚠️ An estimator must not mutate the asset it's estimating

Scaling down locally before the payload stage is right for a production request path and wrong here. Silent downscaling quotes a price for a file the user didn't upload — and resolution is a quality decision, not a cost decision. Losing OCR fidelity on a dense contract to save tokens is the client's call.

Rung 4 needs its own rule, because "downscale = cheaper" is often false. Tiles are a ceiling function, so a resize that doesn't cross a boundary changes nothing — and several providers upscale anything below their shortest-edge target, so shrinking too far can raise the tile count.

Only propose a saving you actually recomputed 
propose_resize ONLY IF
    tiles(scaled_w, scaled_h) < tiles(original_w, original_h)
    AND scaled_shortest_edge >= shortest_edge_target_px

Fidelity floors are per script. Arabic loses diacritics and dot placement first — ب ت ث ن ي differ only by dots — and CJK loses stroke separation early. Latin prose is the most tolerant, and the other two must not be derived from it. Mixed content takes the strictest floor present, never the average.

⚠️ Capacity never outranks residency

"Send the oversized document to whichever model has the largest capacity" is exactly how a KSA client's contract reaches a PRC-hosted endpoint because it was a few hundred pixels too wide. Residency and is_prc_hosted are evaluated before capacity, always — and a reroute no permitted model can absorb is rung 7, not a quiet exception.

Every reroute writes an assumption and shows the substitution inline in the results table. The user asked about model X and is being quoted model Y; that must never be discoverable only via a tooltip.

Calibration, not invention

Character-to-token ratios are generated from observed API responses, never authored by hand — each row storing sample size, mean, p90 and standard deviation, with confidence downgrading automatically when the sample is thin or the calibration is stale. The corpus buckets are en, ar, zh-Hans, code, json, mixed. Arabic is a first-class bucket, not an afterthought — its inflation behaviour sits nowhere near either English or Chinese.

## A3. NON-NEGOTIABLE DATA INTEGRITY RULES (violating these is a P0)

   effective_from, effective_to.
2. REFUSE, DON'T GUESS. Missing, expired or stale rate => needs_human_review: true
   and an entry in missing_data[]. NEVER substitute a similar model's price.

4. ASSUMPTIONS ARE LABELED, NEVER SILENT. Reasoning overhead, cache-hit ratio,

5. CONFLICTS ARE REPORTED, NOT MERGED. If two sources disagree beyond tolerance,

## A4.4 LAYER 0 — INTENT PARSER & THE DEFAULTS ENGINE

Everything in A5 assumes a structured task graph already exists. This section builds
the thing that produces it, from a sentence a human typed in ENGLISH, ARABIC or
CHINESE — and it is where most naive implementations go wrong.

### A4.4.1 Two layers, deterministic first
  [free text, any language]
        v
  [L1 Deterministic Router]  lexicon + normalizer + regex. Free, ~0ms, no tokens.
        v   parse_confidence >= PARSE_CONFIDENCE_FLOOR ? emit : escalate
  [L2 Structured LLM Parse]  PART B prompt, cheapest capable model, JSON mode
        v
  [WorkflowInput]            workflow-input.schema.json

L1 handles the ~70% of inputs that are imperative and well-formed. L2 is the
FALLBACK, not the default.

THE RECURSION NOBODY ACCOUNTS FOR: THE PARSER COSTS MONEY. L2 is itself an LLM call
with input, output and (if you pick a reasoning model — don't) reasoning tokens. A
cost calculator that doesn't meter its own parser is lying about total cost of
ownership. Emit the parse as a `system_overhead` line on every estimate, and expose
L1 hit-rate as an operating metric — it is the single lever on your gross margin.

### A4.4.2 Normalize before you match (where Arabic and Chinese break)
ARABIC — apply in order before any lexicon lookup:
  1. Strip tashkeel/diacritics — the same verb appears with and without them
  2. Normalize alef forms: أ إ آ ٱ -> ا
  3. Normalize ة -> ه, ى -> ي per your matcher's tolerance
  4. Strip prefixes و ف ب ك ال ولل and pronominal suffixes ه ها هم ني نا ك
  5. Convert Arabic-Indic numerals ٠١٢٣٤٥٦٧٨٩ to Western BEFORE any quantity regex.
     A regex that only matches [0-9] silently drops every number in an Arabic
     prompt; the dropped quantity becomes a default, and the default becomes a
     confident wrong estimate.
  6. Match against a normalized-root lexicon, not surface forms

CHINESE — no whitespace, so segmenting the INSTRUCTION is its own problem:
  1. Normalize Traditional -> Simplified (or match both) before lookup
  2. Longest-match segmentation against the verb lexicon, not char-by-char
  3. Convert Chinese numerals 一二三四五六七八九十百千万 and 两 to Western integers
     before quantity extraction — 五份合同 is FIVE contracts, and [0-9]+ sees zero
  4. Measure words 份 篇 张 个 页 条 follow a count and are your strongest
     quantity signal

ALL SCRIPTS — detect script by Unicode range PROPORTIONS, not one label. Gulf
documents are routinely mixed: an Arabic contract with English legal terms, Western
numerals and a Chinese counterparty name. Emit
script_mix: { arabic: 0.71, latin: 0.24, han: 0.05 } — the tokenizer follows the
mix, not the majority.

### A4.4.3 The action lexicon (seed — extend from real usage logs)
READ   EN upload, read, analyze, scan, extract, parse, OCR, ingest, classify,
          compare, search
       AR ارفع، حمّل، اقرأ، حلّل، افحص، استخرج، صنّف، قارن، ابحث
       ZH 上传、读取、阅读、分析、扫描、提取、解析、分类、对比
WRITE  EN write, draft, generate, create, compose, brainstorm, outline, expand, reply
       AR اكتب، صغ، أنشئ، ولّد، اقترح، خطّط، وسّع
       ZH 写、撰写、起草、生成、创建、头脑风暴、扩写
EDIT   EN fix, rewrite, modify, update, change, refine, polish, inpaint, upscale
       AR عدّل، أصلح، أعد صياغة، حدّث، غيّر، نقّح، حسّن
       ZH 修改、修复、改写、更新、润色、重绘、放大

TWO MISCLASSIFICATIONS TO FIX — BOTH UNDERCOUNT:
  translate / ترجم / 翻译   NOT read-only. READ + WRITE: ingests the entire source
      AND emits a full-length target. Classifying it as READ undercounts output by
      roughly one whole document. On a long contract that is the dominant term.
  summarize / لخّص / 总结    NOT write-only. READ + WRITE: ingests the entire source,
      emits a short output. Classifying it as WRITE undercounts INPUT by the whole
      document.

So the lexicon maps VERB -> TASK SEQUENCE, not verb -> task:
  // /packages/router/lexicon.ts
  const COMPOUND = {
    translate: [ {type:'READ',  sub_kind:'context_ingestion'},
                 {type:'WRITE', sub_kind:'completion',
                  ratio_hint:'OUTPUT_APPROX_EQUALS_INPUT'} ],
    summarize: [ {type:'READ',  sub_kind:'context_ingestion'},
                 {type:'WRITE', sub_kind:'completion',
                  ratio_hint:'OUTPUT_MUCH_SMALLER_THAN_INPUT'} ],
    review:  [ /* READ + WRITE — findings are output */ ],
    audit:   [ /* READ + WRITE */ ],
    compare: [ /* READ x n sources + WRITE */ ],
  }
Expanded tasks carry expands_from: "<parent_task_id>" so the UI can show one user
intent as its two billable halves. That display — "you said summarize, here are the
two things you are paying for" — is the product's best explanation of itself.

ALSO HANDLE:
  NEGATION    "don't summarize, just extract" / "لا تلخّص" / "不要总结". A bare keyword
              matcher scores a summarize hit inside a negation. Scan a negation
              window before accepting a match; escalate to L2 on ambiguity.
  CONDITIONALS "summarize it if it's over 10 pages" is a probabilistic branch. Record
              execution_probability and multiply volume. Never treat it as certain.
  ITERATION   "for each", "لكل", "每个", "batch of", and bare plurals all set volume.
              Missing iteration language is the most common cause of a 100x
              underestimate.

### A4.4.4 The defaults engine — and the line it must not cross
Users don't supply pixel dimensions in casual prompts, and refusing to estimate
without them makes the product useless. But that collides with A3 rule 2. One clean
line resolves it:

  GUESS QUANTITIES. NEVER GUESS RATES.
  A missing RATE (price, tile constant, throughput) BLOCKS the estimate — there is
  no honest default for what a vendor charges.
  A missing QUANTITY (document length, image size, turn count) gets a LABELED,
  EDITABLE default that downgrades confidence.

Every default that fires must:
  1. emit an assumptions[] entry with basis "DEFAULT_APPLIED" and an impact rating
  2. render in the Assumptions panel as an editable field, pre-focused when it is
     the top sensitivity driver
  3. downgrade the task to at most MEDIUM confidence; LOW when two or more defaults
     stack on one task
  4. NEVER fire when a real asset is attached — a measured value always beats a
     default. Defaults are for pre-upload and hypothetical estimation only.

SEED BASELINES — enter the DB tagged provenance: SEED_UNCALIBRATED, confidence: LOW,
with a standing task to replace each from observed runs. Starting points, not facts.
Store in `defaults_seed` with source "USER_SUPPLIED_BASELINE" — not in code, and
never shown in the UI as a measured figure.
  short_form   tweet, email, post · تغريدة، منشور · 推文、帖子     300 in /   200 out
  medium_form  article, report   · مقال، تقرير  · 文章、报告   2,000 in /   800 out
  long_form    book, contract, multi-page PDF · عقد · 合同    25,000 in / 2,000 out
  image        unspecified image · صورة · 图片              1024x1024, detail=high

### A4.4.5 Language-inflation defaults — three corrections
The rule "if Chinese, multiply character count by 1.5-2.5x" has three problems:
  1. MULTIPLIER RELATIVE TO WHAT? No stated baseline. Written properly the heuristic
     is tokens ~= chars * ratio[model, script] — one MEASURED ratio per (model,
     script) pair. Store the ratio; never a multiplier-of-a-multiplier.
  2. A 1.5-2.5x BAND IS A +/-25% COST SWING before anything else varies. That is not
     a range you pick from — it is a distribution. Emit P50 and P90 or the user
     reads the low end as the price.
  3. YOU WILL ALMOST NEVER NEED IT. Qwen, GLM, DeepSeek and the OpenAI families all
     have local exact tokenizers. The ratio path is only for PROXY tokenizers,
     offline preview and pre-upload estimates. Applying a ratio when an exact count
     is available is a self-inflicted error.

ARABIC NEEDS ITS OWN MEASURED RATIO plus three rules the Chinese path lacks:
  TASHKEEL IS BILLABLE. Fully vocalized Arabic (Qur'anic, liturgical, pedagogical,
     formal legal) carries a diacritic on nearly every consonant and most tokenizers
     treat them as separate tokens. Detect diacritic density and BRANCH — do not use
     one Arabic ratio for both.
  MORPHOLOGY, NOT SPACES. Arabic packs article, conjunction, preposition and pronoun
     into one orthographic word. Calibrate on characters, per model; word-based
     ratios behave much worse.
  DIALECT vs MSA. Gulf and Levantine content tokenizes worse on MSA-weighted models.
     If Jordan/KSA/Kuwait workloads include chat or social content, that is a
     separate calibration bucket from contracts.

CORPUS BUCKETS become: en, ar_msa, ar_dialect, ar_vocalized, zh_hans, zh_hant, code,
json, mixed — each with its own n_samples, mean, p90, stddev.

### A4.4.6 Three language fields, not one
"I want to upload a Chinese contract PDF, summarize it, and generate a featured
image" is written in ENGLISH about a CHINESE payload, possibly from an ARABIC UI.
Conflating them is a direct mispricing.
  "languages": {
    "ui_language":          "ar",     // interface locale — costs nothing, drives RTL
    "instruction_language": "en",     // language of the request — lexicon selection
    "payload_languages": [            // language of the BILLED CONTENT
      { "code": "zh-Hans", "share": 0.95 },
      { "code": "en",      "share": 0.05 }
    ]
  }
ONLY payload_languages enters the cost math.

### A4.4.7 Is the PDF scanned? (the question that example hides)
"Upload a Chinese contract PDF" is two completely different cost models:
                  TEXT-LAYER PDF              SCANNED PDF
  Task type       READ · context ingestion    READ · VISION OCR
  Cost driver     text tokens                 IMAGE TILES, PER PAGE
  Formula         A5.1                        A5.2, once per page
  Magnitude       baseline                    far higher, scales with page count
The parser MUST NOT choose silently. Detect it when the asset is present (text layer
+ character count); when absent, put it in missing_data[] as a BLOCKING question —
"Is the PDF searchable text or a scan?" — because no default is defensible across a
gap this size. Same question for images inside DOCX and for photographed documents,
which are near-universal in Gulf contract workflows.

WORKED TRACE, once Layer 0 is correct:
  "I want to upload a Chinese contract PDF, summarize it,
   and generate a featured image for the article"
  -> languages: instruction=en, payload=[zh-Hans], ui=<session>
  -> t1 READ  context_ingestion | doc_class=long_form | zh-Hans
        BLOCKING: text-layer or scanned? (-> vision_ocr if scanned)
        default:  25,000 input tokens   [SEED_UNCALIBRATED · editable]
  -> t2 READ  context_ingestion | expands_from=summarize   <- commonly missed
  -> t3 WRITE completion        | expands_from=summarize
                                  ratio_hint=OUTPUT_MUCH_SMALLER_THAN_INPUT
  -> t4 EDIT  image_generate    | per-image pricing, NOT tokens (A7)
        default:  1024x1024              [SEED_UNCALIBRATED · editable]
  -> confidence: LOW · needs_human_review: true
  -> missing_data: [pdf_has_text_layer, image_dimensions, target_summary_length]

FOUR TASKS FROM THREE VERBS, TWO BLOCKING QUESTIONS, AND LOW CONFIDENCE — from a
sentence that looks completely unambiguous. That gap is why Layer 0 exists.

## A4.5 TIERED TOKEN ESTIMATION ENGINE (Tier 0 → Tier 3)

No single counting method is right for every request. Four tiers, each mapping to a
declared `method` tag, a default confidence, and an explicit escalation trigger.
/packages/tokenizers exposes ONE function — estimateTokens(payload, model, mode) —
and the tier it used is part of the return value, never a hidden detail.

  TIER 0  inherits cached tier    ~0        inherits   cache hit on identical payload
  TIER 1  PROVIDER_COUNT_API      network   HIGH       media payloads; near a context
                                                       or price boundary; committing
                                                       a quote
  TIER 2  EXACT_TOKENIZER/PROXY   sub-ms    HIGH/LOW   text-only, local vocabulary
  TIER 3  CALIBRATED_HEURISTIC    0         MED→LOW    offline preview, typing
                                                       indicator, pre-upload sizing

### A4.5.1 Tier 0 — cache, and the key that makes it safe
Content-hash the payload, but THE HASH ALONE IS NOT THE KEY:

  // /packages/tokenizers/cache-key.ts
  cacheKey = sha256(canonicalizeMessages(messages))
           + ':' + model_id
           + ':' + tokenizer_revision       // the pinned artifact hash from A4.1
           + ':' + chat_template_version    // framing overhead changes with it
           + ':' + tenant_id                // never share a cache across tenants

OMITTING model_id OR tokenizer_revision IS THE SINGLE MOST LIKELY BUG IN THIS DESIGN.
The same message array tokenizes differently on different models, and differently on
the SAME model after a tokenizer artifact bump. A hash-only key silently serves one
model's count for another, forever, with HIGH confidence attached. Bumping
tokenizer_revision must invalidate BY CONSTRUCTION — never by a manual flush.

canonicalizeMessages must be byte-stable: stable key order, no incidental whitespace,
deterministic tool-schema serialization. An unstable canonicalizer gives a 0% hit
rate that looks like a working cache.

Payload content is hashed, not stored. Where a tenant's policy forbids even hashed
derivatives of regulated content leaving their boundary, the cache is per-tenant and
co-located — which is why tenant_id is IN the key, not a namespace bolted on later.

### A4.5.2 Tier 1 — remote count API is ground truth
Use for: any payload containing media; any estimate within TIER_PROXIMITY_WARN_PCT of
a context-window or price-tier boundary; any figure the user commits as a quote.

GEMINI: multimodal token weight depends on resolution downscaling and temporal frame
sampling, which the local path does not replicate. The local path must DETECT MEDIA
AND REFUSE — not silently count the text portion, which produces a large, confident
undercount. Local Gemini is a text-only optimization; media always escalates.

ANTHROPIC: rate-limit the adapter on its own bucket (A10), cache by the key above,
and treat a 429 as a DOWNGRADE to Tier 3 with a visible badge — never a silent zero.

EVERY TIER 1 CALL IS ALSO A FREE CALIBRATION SAMPLE. When the remote count returns,
compute what Tier 2 and Tier 3 WOULD HAVE SAID for the same payload and write the
deltas to the calibration store. The heuristic improves as a by-product of normal
operation, and proxy drift surfaces as a widening delta before it becomes a wrong
invoice. Wire this from day one — retrofitting means discarding every sample you
already paid for.

### A4.5.3 Tier 2 — local and proxy tokenizers
Exact local vocabularies (A4.1) run here at HIGH confidence. Proxies do not.

PROXY SELECTION RULE — MATCH THE SCRIPT, NOT JUST THE ARCHITECTURE. "Map to a standard
LLaMA/Qwen baseline" treats those two as interchangeable; for Chinese they are not. A
Chinese-native vocabulary and an older Western-trained vocabulary fragment Hanzi very
differently, so proxying a Chinese closed-tier model (ERNIE, Hunyuan) to a
Western-trained tokenizer is wrong in a CONSISTENT DIRECTION — the worst kind of
error, because it looks stable. Proxy Chinese to Chinese-native; Western to Western.

  "tokenizer_proxy": {
    "target_model": "<closed-tier model>",
    "proxy_model":  "<script-matched open-weight model>",
    "basis": "SCRIPT_AND_ARCHITECTURE_MATCH",
    "measured_delta_pct": null   // from Tier 1 drift capture; null = unvalidated
  }

Until measured_delta_pct has samples, every proxy count is confidence: LOW and raises
PROXY_TOKENIZER_IN_USE. A proxy whose measured delta exceeds PROXY_DRIFT_MAX_PCT is
DISABLED and that model falls back to Tier 1 only.

### A4.5.4 Tier 3 — heuristics, and the constant you may not generalize
Bootstrap value, COLD START ONLY: approximately 3.5-4 characters per token for ENGLISH
PROSE, plus per-model fixed offsets for media blocks. It enters defaults_seed tagged
provenance: SEED_UNCALIBRATED, confidence: MEDIUM, and is REPLACED AUTOMATICALLY by the
calibration table (A4.1) once n_samples crosses threshold. Never written into source.

THAT FIGURE IS ENGLISH PROSE ONLY. DO NOT GENERALIZE IT.
  English prose         bootstrap ratio permitted, MEDIUM
  Code / JSON / tabular own calibration bucket — tokenizes very differently
  Arabic (any register) NO BOOTSTRAP VALUE EXISTS HERE. Unavailable until calibrated.
  Chinese (Hans/Hant)   NO BOOTSTRAP VALUE EXISTS HERE. Unavailable until calibrated.

Applying the English ratio to Arabic or Chinese is the failure this section exists to
prevent — confident, silent, and wrong by a large factor. When a script has no
calibration row, Tier 3 returns UNAVAILABLE with a specific missing_data[] entry ("no
calibration samples for ar_vocalized on this model") and the UI shows a live CHARACTER
count instead of a fake token count. A blank token field is honest; a wrong one is not.

### A4.5.5 Two numbers, not one — padding is directional
A +15% safety buffer is correct for one consumer and wrong for the other:
  CONTEXT-OVERFLOW CHECK  wants to OVER-estimate; a wrong guess must fail safe  + buffer
  COST ESTIMATE / QUOTE   wants to be CENTRED; padding inflates the quote       none

So Tier 3 emits BOTH, separate all the way to the UI:
  cost_estimate           = raw heuristic → P50/P90, feeds A5.8
  context_safety_estimate = raw x (1 + HEURISTIC_SAFETY_PAD_PCT)
                            → feeds context-window and max_tokens checks ONLY

HEURISTIC_SAFETY_PAD_PCT is a config value, not a literal, and applies to TIER 3 ONLY
— padding a Tier 1 ground-truth count is just overquoting. The padded number must
NEVER reach a price.

### A4.5.6 Processing flow (implement exactly)
  estimateTokens(payload, model, mode)

  1. Tier 0 — cache lookup on the composite key. Hit -> return with the CACHED tier's
     method and confidence. Never re-tag a cached Tier 3 value as Tier 1.

  2. mode == LIVE_UI or OFFLINE
       -> Tier 2 if a local exact vocabulary exists AND payload is text-only
       -> else Tier 3, if a calibration row exists for (model, script, content_type)
       -> else UNAVAILABLE + missing_data[]. Show a CHARACTER count, not a token count.

  3. mode == ESTIMATE or COMMIT, or ANY of:
       - payload contains image / audio / video
       - result is within TIER_PROXIMITY_WARN_PCT of a context window or price tier
       - tokenizer_availability is PROXY and measured_delta_pct is null
       - the user is committing this figure as a quote
     -> escalate to Tier 1. On 429 / timeout / offline, fall back ONE tier, RE-TAG the
        line with the tier actually used, and raise ESCALATION_FAILED. Never present a
        fallback number wearing the confidence of the tier you wanted.

  4. Write through to cache. If Tier 1 ran, compute the Tier 2 and Tier 3
     counterfactuals and append the deltas to the calibration store (A4.5.2).

THE INVARIANT ACROSS ALL FOUR TIERS: the method and confidence on the returned line
describe the tier that ACTUALLY PRODUCED THE NUMBER, never the tier that was
requested. Every downgrade is visible in the UI. A silent downgrade is the same class
of bug as a hardcoded rate.

### A4.6.1 THE GEOMETRY PROBE
Where a provider publishes no formula, one API call per probe point returns
usage.prompt_tokens; subtract a text-only baseline and the remainder is the visual-
token count. That settles in an afternoon what documentation has failed to settle,
and turns an UNAVAILABLE row into a sourced one.

DESIGN RULES — the honesty contract applied to measurement:
1. SPEND MONEY ONLY ON PURPOSE. --dry-run is the DEFAULT and prints a deliberately
   pessimistic cost upper bound; --confirm is required to make a call; --max-calls is
   a hard stop. Cache every result to disk so a crash costs nothing twice. Pin
   max_tokens:1 — you are measuring the INPUT side; paying for output buys nothing.
2. RUN A CONTROL MODEL FIRST, AND REFUSE TO TRUST THE RUN WITHOUT IT. Pick a model
   whose geometry IS published, with known worked answers, and probe it in the same
   harness. A wrongly subtracted baseline, a provider silently re-encoding the
   upload, a `detail` parameter being ignored — every one produces PLAUSIBLE NUMBERS
   AND A WRONG FORMULA. If the harness cannot recover the control's known geometry,
   EVERY OTHER RESULT IN THE RUN IS WORTHLESS. This is the most important line here.
3. CHOOSE PROBE POINTS TO DISCRIMINATE, NOT TO SAMPLE. Every candidate geometry is
   roughly monotonic in area, so most sizes agree and teach nothing. The information
   sits at boundaries where candidates disagree: one pixel either side of each
   candidate's block/tile size, exact multiples of each candidate patch size, and the
   extremes that exercise caps and clamps.
4. INCLUDE A TRANSPOSED PAIR — THE DECISIVE MEASUREMENT. Patch grids, tile grids,
   area budgets and flat rates are all commutative, so w×h and h×w return the same
   count. A geometry with a width-dependent term does not. EQUAL COUNTS RULE OUT
   EVERY ASYMMETRIC FORMULA IN ONE COMPARISON; unequal counts prove any tile-grid
   implementation is wrong for that model. One pair of calls halves the candidate set.
5. NEVER RETURN A BEST GUESS. A candidate explaining most points is a coincidence
   with counterexamples. Report a fit only when the residual is ZERO across EVERY
   observation; anything else is UNKNOWN with the misses listed. Two exact fits is
   also not a result — it means the grid does not discriminate: add sizes that
   straddle their differing boundaries and re-run.
6. A MEASUREMENT IS EVIDENCE, NOT A REGISTRY ENTRY. The probe writes a generated JSON
   file for a human to review. It does not write to the pricing registry. A3 applies
   to measured constants exactly as to sourced ones.
7. FAIL LOUDLY AND SPECIFICALLY. A provider that does not report prompt tokens cannot
   be probed by this method — say so rather than inferring a number from something
   else in the response. Context overruns recorded as skipped, errors as errors, both
   with the message. Do not retry an auth failure or a rejected image; retrying spends
   money on a request that will fail identically.

PROBE IMAGES MUST BE DETERMINISTIC AND BYTE-IDENTICAL ACROSS MACHINES — that is what
makes the cache key honest on a resumed or shared run. Generate them WITHOUT an image
library: a library may silently re-encode, strip or resample, and when the entire
question is "what pixel dimensions did the provider actually see", a library between
you and the bytes is an uncontrolled variable. Avoid a flat fill (a provider may
short-circuit on trivial content, and byte size is unrealistic) and avoid per-pixel
noise (incompressible — the largest and most informative probe point will fail on a
FILE SIZE limit rather than on geometry). Deterministic coloured blocks sit between.

Test the fitter against SYNTHETIC data generated from geometries you already know, so
tests run offline and cost nothing. The NEGATIVE cases matter more than the positive
ones: a fitter that always returns something is worse than useless, because it
launders a guess into a measurement.

## A5.9.1 THE VLM CHAIN — VISUAL TOKENS HAVE TWO DESTINATIONS

Vision geometry and VRAM sizing are usually written as separate concerns, and that
split is where VLM estimates go wrong. THE GEOMETRY OUTPUT IS THE SIZING INPUT:

  pixels --[A5.2 geometry]--> visual_tokens --+--> hosted:      x input_rate
                                              +--> self-hosted: x KV bytes/token -> VRAM

  kv_cache = 2 * layers * kv_heads * head_dim * bytes_per_param(kv_dtype)
                * MIN(visual_tokens + text_context_tokens, max_context)

One quantity, two destinations — SO A GEOMETRY ERROR PROPAGATES INTO BOTH. A 34%
visual-token undercount is a 34% KV-cache undercount, which turns a "fits
comfortably" cell into an out-of-memory crash under load.

VISUAL TOKENS MUST ALSO FEED THE CONTEXT-WINDOW GATE, NOT JUST THE COST LINE. The
annex documents a VLM whose max context is small enough that a SINGLE ordinary-
resolution image consumes roughly HALF of it — two images plus a prompt do not fit at
all. That is a CAPABILITY LIMIT WEARING A COST LIMIT'S CLOTHES, and it is invisible in
a VRAM table (the KV cache clamps to a reassuringly small number, which is exactly
backwards). So: carry max_context on every vision row and compute
image_share_of_context; raise CONTEXT_TOO_SMALL from the VISUAL token count, not only
from text; clamp the KV term by MIN(tokens, max_context).

PREFILL DOMINATES DECODE ON DOCUMENT WORK. A multi-thousand-token image answered in a
couple hundred tokens makes prefill the overwhelming majority of compute — the
OPPOSITE of a chat workload. For document VLM sizing the bottleneck is
prefill_throughput_tps, not decode_throughput_tps.

FOUR ERRORS AVAILABLE IN THE VRAM GATE, DESCENDING BY SIZE:
1. kv_heads, NOT attention heads. Under GQA a model may expose many query heads and
   few KV heads; using the query count can overstate KV cache by ~7x. Not every model
   HAS GQA — where num_key_value_heads == num_attention_heads it makes no difference,
   which is why the code must READ the field rather than assume the architecture. A
   smaller model with full MHA can hold MORE KV per token than a larger GQA model.
   Nothing in a parameter count predicts that.
2. MIXTURE-OF-EXPERTS WEIGHTS USE TOTAL PARAMETERS, NOT ACTIVE. Every expert stays
   resident; only THROUGHPUT reflects the active subset. Sizing on active params
   understates weight VRAM by roughly the expert ratio.
3. FLASHATTENTION DOES NOT REDUCE THE KV CACHE. It avoids materialising the attention
   matrix, cutting ACTIVATION memory. What does reduce KV cache: grouped-query
   attention (architectural, already in the formula), paged attention (removes
   fragmentation waste rather than compressing), and KV QUANTIZATION — set kv_dtype
   independently of weight quantization. Keep supports_flash_attention away from the
   kv_cache term in code, or the next person will reintroduce this.
4. gpu_memory_utilization CAPS THE ENGINE'S TOTAL FOOTPRINT — weights plus KV plus
   activations — not a reserve earmarked for anything. The remainder covers CUDA
   context and fragmentation.

And one rule of thumb that does NOT generalise: "GB per 32k tokens" figures are
model-specific. A deep model with few KV heads and a shallow one with many differ by
an order of magnitude for the same context. COMPUTE THE TERM; never carry the
constant across model sizes.

served_quantization MATTERS FOR PRICE COMPARISON, NOT JUST SIZING. A provider serving
a model at FP8 or INT4 is not serving the same artifact as one serving it at BF16,
even under the same model name. A comparison ignoring quantization compares different
models.

## A5.10 REQUEST-LEVEL MULTIPLIERS AND NON-TOKEN FEES

The identity in A5.8 covers what is metered per token. Vendor pages carry three more
layers that it does not, and each moves a real invoice. THESE BELONG ON THE REQUEST,
NOT THE MODEL ROW — the same model under two service tiers is two different answers
from one registry entry.

  FINAL_COST = ( TOKEN_TERMS(A5.8)
               + cache_storage_tokens * storage_rate_per_1m_per_hour * hours_held
               + tool_use_system_prompt_tokens * input_rate
               + SUM(server_tool_calls * per_call_fee) )
             * service_tier_multiplier
             * (1 + residency_uplift_pct)

  SERVICE TIER MULTIPLIER  batch/flex/fast/priority scale the WHOLE bill. It is a
    REQUEST attribute, so a row-level registry has nowhere to put it. The multipliers
    are NOT SHARED ACROSS VENDORS — the annex records one provider's premium tier at
    1.8x where two others use 2x. Store per provider, never as a shared constant.
  RESIDENCY UPLIFT  regional/in-country endpoints carry a percentage uplift on ALL
    categories, cache reads and writes included. THIS BINDS DIRECTLY ON GULF ROUTING:
    the compliant option is not the same price as the default, and a router that
    filters on residency without applying the uplift understates the compliant path.
  CACHE STORAGE PER HOUR  at least one provider bills cached content BY THE HOUR
    WHETHER OR NOT YOU CALL THE MODEL. Every cache model in this spec until now
    assumed write+read only. PER-PROVIDER FIELD, nullable — a long-lived cache on a
    low-traffic workload can cost more than it saves, and the estimator must show it.
  TOOL-USE SYSTEM PROMPT  a published per-model token count for merely ENABLING
    tools, SEPARATE FROM AND ADDITIONAL TO the tool schema JSON in A5.1. Two meters,
    both real; one provider reports tool tokens as its own usage field.
  SERVER-TOOL PER-CALL FEES  web search, file search, code containers: NOT
    TOKEN-PRICED AT ALL. Per thousand calls, per GB-day, or per session. A token-only
    estimator returns ZERO for them; an agentic workflow with search enabled can have
    a majority of its cost here.
  FAILED GENERATIONS  bills_failed_generations is published on at least one video
    model. Assuming either way is a guess. Where it bills, expected_retry_rate is a
    labelled assumption.
  RE-ROLLS  image workflows generate N candidates per accepted image and EVERY
    CANDIDATE BILLS. candidates_per_accepted_image is a required task field,
    defaulting to 1 and almost never actually 1.

TWO SHAPE CORRECTIONS TO A5.7:
  - NOT EVERY MODEL HAS CONTEXT TIERS. At least one provider includes its full long
    context at the standard rate, so context_tiers is NULL for that family — not a
    single-entry array and not an assumed surcharge.
  - A TIER CAN REBILL THE WHOLE REQUEST, NOT THE OVERFLOW. Where crossing a threshold
    reprices EVERY token rather than the excess, the step is far larger than a
    marginal reading suggests. applies_to_whole_request: boolean on each tier, and
    the near-threshold warning must use the right one.

IMAGE GENERATION HAS A FOURTH PRICING DIMENSION. per_image | per_megapixel | per_step
is incomplete: some providers meter image output IN TOKENS and the per-image figure is
DERIVED (tokens_for_resolution * output_rate). Add per_output_token and store the
resolution->token map, rendering the derived per-image figure as authoritative with the
token figure as explanation. Where a vendor sells only a SUBSCRIPTION,
pricing_model:'subscription' makes the model NON-COMPARABLE in the router rather than
assigned a synthesized unit price — averaging a monthly fee into a per-image number is
exactly the invented figure A3 exists to prevent.

## A5. THE ESTIMATION ENGINE (/packages/estimator)

### A5.1 Text input tokens
input_tokens = tokenize(rendered_prompt) + framing_overhead + tool_schema_tokens

1. RENDERED PROMPT — actual user + system content through the model's tokenizer.
2. FRAMING OVERHEAD — chat-template scaffolding, role markers, BOS/EOS, message
   separators. Per-model and per-turn. Derive EMPIRICALLY: tokenize a message with
   the template applied, subtract the raw content count, store as
   framing_tokens_per_message in the calibration table. Do NOT assume a constant
   across families.
3. TOOL SCHEMA TOKENS — every tool definition is serialized into context BEFORE the
   user types. Tokenize the actual JSON schema payload. In agentic workflows this
   frequently dominates a short prompt.

Language inflation is handled by the tokenizer itself when method is
EXACT_TOKENIZER — no ratio needed. Ratios apply only in CALIBRATED_HEURISTIC mode
(fast preview, offline, or PROXY-tokenizer models).

### A5.2 Vision / image input
Cost is a function of PIXEL DIMENSIONS and DETAIL MODE, not file size.

THERE IS NO SINGLE VISION FORMULA. DO NOT WRITE ONE. The tile grid
`base + per_tile × ceil(w/tw) × ceil(h/th)` is ONE geometry among at least six in
production; implementing it as a universal misprices most non-OpenAI vision models,
silently and in a consistent direction. vision_profile.geometry selects the branch.
An unknown geometry is UNAVAILABLE — never defaulted to the familiar one.

  G1a PATCH_GRID + TOKEN_CAP    patches=ceil(w/P)*ceil(h/P), scale until <= cap
                                COST SATURATES — bigger image, same price, less detail
  G1b PATCH_GRID + AREA_CLAMP   round dims up to multiple of P, clamp area into
                                [min,max], tokens=(w/P)*(h/P)
                                COST DOES NOT SATURATE — expensive and faithful
  G2  TILE_GRID                 base + per_tile * ceil(w/tw) * ceil(h/th)
  G3  AREA_BUDGET               min(budget, area_px / divisor) — SMOOTH, no ceiling
  G4  FLAT                      constant regardless of dimensions — SUPPRESS resize
                                proposals entirely, they save nothing by construction
  G5  BLOCK_GRID_SEP            (h*w + 1) * per_block + (w + 1) * sep + const
                                global-view term + WIDTH-DEPENDENT separators

G1a AND G1b ARE THE SAME PATCH SIZE AND PRODUCE WILDLY DIFFERENT ANSWERS. Per Annex
A15 §3 (vendor pages, verified 2026-09-06) Claude, Qwen-VL and GLM-4.1V all use a
28px patch grid — Claude bounds on a TOKEN CAP, the two Chinese models on a PIXEL
AREA range. On the same oversized scan Claude saturates in the low thousands while
Qwen-VL runs to five figures: an order of magnitude, from a formula identical on
paper. bound_type ∈ {TOKEN_CAP | AREA_CLAMP} is a required field with min_area_px /
max_area_px. A router comparing them on price alone, without source dimensions, will
be wrong about which is cheaper.

TOKEN COST IS NOT MONOTONIC IN PIXEL COUNT UNDER G5. The annex documents a
DeepSeek-VL2 case where a LARGER image costs FEWER tokens, because block selection
lands on a cheaper grid. Independent confirmation that rung 4 of the disposition
ladder must actually RECOMPUTE rather than reason about direction.

WIRE COMPATIBILITY PREDICTS NOTHING ABOUT BILLING GEOMETRY. Every Chinese VLM checked
speaks the OpenAI protocol and accepts the same detail:low|high parameter, and not
one uses OpenAI's geometry.

### A5.2.0b EVALUATE `detail` BEFORE GEOMETRY
detail:low is a FLAT RATE on every Chinese VLM checked — a constant regardless of
dimensions. On those models low-detail mode IS geometry G4, so branch order matters:
  1. resolve detail mode
  2. if low_detail_geometry == FLAT -> return low_detail_flat_tokens. STOP.
  3. otherwise branch on vision_profile.geometry
Resolving geometry first and applying the flag afterwards is wrong by a large factor
on exactly the models where detail:low is most attractive.

And note what that makes detail:low — on a large scan it is a very large token
reduction AND the setting that destroys Arabic dot placement and diacritics first
(A5.2.1). IT IS A QUALITY DECISION WEARING A COST DECISION'S CLOTHES. Surface both
numbers; never select it automatically to flatter an estimate.

### A5.2.0c REQUIRED vision_profile FIELDS
  geometry ∈ {PATCH_GRID|TILE_GRID|AREA_BUDGET|FLAT|BLOCK_GRID_SEP}
  bound_type ∈ {TOKEN_CAP|AREA_CLAMP}      <- patch grids differ on this
  patch_px | tile_w,tile_h    base_tokens   per_tile_tokens
  token_cap | min_area_px,max_area_px       area_divisor  area_budget_tokens
  flat_tokens_per_image       low_detail_flat_tokens
  low_detail_geometry ∈ {FLAT|INHERIT}
  block_px  global_view_included  sep_tokens_per_row  sep_constant  max_blocks
  candidate_resolutions[]                  <- where selection is a bounded lookup
  max_edge_px min_edge_px shortest_edge_target_px max_bytes max_pages allowed_mime[]
  provider_auto_normalizes    min_legible_edge_px[script, density]

A schema refinement must enforce that each geometry carries its own parameters and no
others': a TILE_GRID row with a null per_tile_tokens silently prices every image at
base_tokens, and that is the exact bug the refinement exists to catch.

### A5.2.0d WHEN THE VENDOR CONTRADICTS ITSELF
Vendor docs disagreeing with THEMSELVES on the same page is not hypothetical — the
annex records it on two providers. A3 rule 5 applies to a single source contradicting
itself exactly as to two sources disagreeing: REPORT, DO NOT MERGE, DO NOT AVERAGE.
Seed the variant whose worked examples are internally consistent, flag the row
needs_human_review, and record both readings.

Ship a PRE-FLIGHT DIMENSION CALCULATOR in the client: read intrinsic width/height
before upload, compute the tile grid, show projected token cost BEFORE the user
commits, and warn when a resize would cut cost materially.

### A5.2.1 Oversized and out-of-spec assets — the disposition ladder
The pre-flight calculator DETECTS a violation. This is what happens next. Constraints
are per-model DB fields (max_edge_px, min_edge_px, shortest_edge_target_px, max_bytes,
max_pages, max_duration_seconds, max_frames, allowed_mime[]) — NEVER literals in code,
for the same reason as every other vision parameter.

THIS IS AN ESTIMATOR, NOT AN EXECUTION PIPELINE. IT MUST NOT MUTATE THE USER'S ASSET.
"Scale down locally before it reaches the payload stage" is right for a production
request path and wrong here. Downscaling silently means the user is shown a price for
an asset they did not upload — and worse, RESOLUTION IS A QUALITY DECISION, NOT A COST
DECISION. Losing OCR fidelity on a dense contract to save tokens is the client's call,
not the pipeline's. The engine COMPUTES BOTH SCENARIOS AND PROPOSES; never rewrites.

THE LADDER — evaluate in order, stop at the first rung that resolves:
  0 MEASURE               always — true intrinsic dimensions, bytes, page/frame count,
                          MIME by magic bytes. Provenance MEASURED_FROM_ASSET.
  1 FITS_AS_IS            within every constraint -> estimate normally, no flag
  2 PROVIDER_NORMALIZED   provider scales it itself before billing -> compute tiles on
                          the POST-NORMALIZATION dimensions, not the user's. Tag
                          DERIVED_FROM_ASSET and name the rule applied.
  3 RESIZE_PROPOSED       over max_edge_px, fidelity not critical -> compute BOTH
                          estimates side by side, present as a choice, pre-select the
                          resize only if it actually saves (rung 4)
  4 RESIZE_SAVES_NOTHING  recomputed tile grid unchanged or larger -> do NOT propose
  5 FIDELITY_LOCKED       user marked OCR-critical, or script floor applies -> skip
                          resize, force explicit high-detail tiling, price the truth
  6 REROUTED              no disposition fits this model -> hand to the capability gate
                          as an exclusion; A7 picks a model that accepts the asset
  7 BLOCKED               violation makes cost unknowable -> missing_data[] +
                          needs_human_review. No number.

RUNG 4 NEEDS ITS OWN RULE, BECAUSE "DOWNSCALE = CHEAPER" IS OFTEN FALSE. Tiles are a
ceiling function, so a resize that doesn't cross a tile boundary changes nothing.
Worse, several providers UPSCALE anything below shortest_edge_target_px, so shrinking
too far can INCREASE the tile count. And a flat low-detail mode may already beat any
resize. So:
    propose_resize ONLY IF
      tiles(scaled_w, scaled_h) < tiles(original_w, original_h)
      AND scaled_shortest_edge >= shortest_edge_target_px
Never show a resize suggestion whose saving you have not recomputed. A suggestion that
saves nothing teaches the user to ignore all of them.

SCRIPT-AWARE FIDELITY FLOORS. Downscaling destroys legibility at very different rates
by script, and this app's workloads are Arabic and Chinese:
  ARABIC   diacritics, dot placement (ب ت ث ن ي differ only by dots) and the ي/ى
           distinction go first. Vocalized or handwritten Arabic has a much higher
           floor than Latin prose.
  CJK      dense glyphs lose stroke separation early; a small point size that survives
           at full resolution becomes an unrecognizable blob.
  LATIN    most tolerant. DO NOT derive the other two from it.
Store min_legible_edge_px per (script, content_density) in the vision profile. Unknown
or mixed script takes the STRICTEST floor present, never the average. Below the floor,
rung 3 is unavailable and the ladder goes to rung 5.

RUNG 6 — REROUTING, AND THE FILTER IT DOES NOT GET TO SKIP. An oversized asset becomes
a capability-gate criterion like any other, with excluded_models[] reason
ASSET_EXCEEDS_CONSTRAINTS naming which constraint and by how much.

REROUTING NEVER OVERRIDES THE DATA-RESIDENCY HARD FILTER (A6). "Send the oversized
document to whichever model has the largest capacity" is exactly how a KSA client's
contract ends up at a PRC-hosted endpoint because it was a few hundred pixels too
wide. Residency, DPA availability and is_prc_hosted are evaluated BEFORE capacity,
always. A reroute no residency-permitted model can absorb is rung 7, not a quiet
exception.

Every reroute writes an assumptions[] entry { field: "routed_model", assumed_value,
basis: "ASSET_CONSTRAINT_REROUTE", impact_if_wrong }, and the results table shows the
substitution INLINE — the user asked about model X and is being quoted model Y, and
that must never be discoverable only by reading a tooltip.

PROVENANCE, CORRECTED. Provenance describes WHERE THE DIMENSION VALUE CAME FROM, and
detail mode is a separate field — changing the tiling mode does NOT change provenance:
  read from the user's file                      MEASURED_FROM_ASSET
  provider normalized it / user accepted resize  DERIVED_FROM_ASSET + transform_rule
  no asset yet, seed default                     DEFAULT_APPLIED

ALSO CONSTRAIN, NOT JUST MAX PIXELS: min_edge_px (below which a provider may reject or
upscale), max_bytes, max_pages for PDFs, max_duration_seconds and max_frames for video,
allowed_mime[] validated by magic bytes (A10). FOR MULTI-PAGE DOCUMENTS THE BLOW-UP IS
PER PAGE — an oversized page multiplies across the whole file, so evaluate the ladder
on the page template, multiply, and surface pages x tiles_per_page as its own estimate
line rather than one opaque total.

WARNINGS THIS RUNG RAISES: ASSET_EXCEEDS_MAX_EDGE, RESIZE_SAVES_NOTHING,
RESIZE_BELOW_LEGIBILITY_FLOOR, PROVIDER_WILL_NORMALIZE, REROUTED_FOR_ASSET_CONSTRAINT,
REROUTE_BLOCKED_BY_RESIDENCY.

### A5.3 Audio / video — duration-driven, not byte-driven
  audio_tokens = ceil(duration_seconds) * tokens_per_second[model]
  video_tokens = frames_sampled * per_frame_image_tokens + audio_track_tokens
tokens_per_second, frame_sample_rate_hz and whether the audio track bills
separately are DB parameters per model. Video is the highest-variance modality —
force confidence: LOW unless the provider publishes a deterministic formula.

### A5.4 Output + reasoning tokens (the non-deterministic half)
  output_tokens    ~ Distribution(p50, p90, cap = max_tokens)
  reasoning_tokens ~ Distribution(p50, p90)   // reasoning-capable models only
  billable_output  = output_tokens + reasoning_tokens

Seed distributions from task_type priors (classify << summarize < draft <
long_form_generate < agentic_multi_step), each CALIBRATED FROM OBSERVED RUNS,
not invented. Reasoning tokens are invisible but billed: for any model flagged
is_reasoning_model a reasoning term is MANDATORY. Capture the provider's
completion-token-details field from real responses from day one — that is what
feeds the prior. Always clamp by max_tokens and warn when the cap sits below P90.

### A5.5 Multi-turn context growth (cost is quadratic-ish, not linear)
  turn_n_input = system + tools + SUM(prior inputs + prior outputs) + new_input
  total_input  = SUM over turns
Model three strategies and let the user pick: FULL_HISTORY, SLIDING_WINDOW(k),
SUMMARIZED_ROLLUP(every_n). Show the total-cost delta between them. This is
usually the biggest optimization lever in a chatbot workflow — put it in the UI,
not a footnote.

### A5.6 Caching
  effective_input_cost = (cached_tokens     * cache_read_rate)
                       + (cache_write_tokens * cache_write_rate)
                       + (uncached_tokens    * standard_input_rate)
cache_read_rate, cache_write_rate, minimum cacheable prefix length and TTL are
per-provider DB fields — providers differ on all four, and some charge a PREMIUM
to write cache. cache_hit_ratio is a user-editable ASSUMPTION, defaulted by
workflow shape, never silently set to a flattering number.

### A5.7 Context-window tier pricing (step function, not a flat rate)
  rate = tiers.find(t => total_input_tokens <= t.upper_bound).rate
tiers[] is a DB array per model. Warn when an estimate lands within
TIER_PROXIMITY_WARN_PCT of a threshold — that is where a small prompt trim
produces an outsized saving.

### A5.8 API-managed cost (canonical)
  API_COST = (billable_input  * input_rate(tier))
           + (billable_output * output_rate)        // includes reasoning tokens
           + (image_tokens    * image_or_tile_rate)
           + (audio_seconds   * audio_rate)
           - (cached_tokens   * (input_rate - cache_read_rate))
           + (cache_write     * cache_write_rate)
           + per_request_fees
Return P50 and P90 of this, per task, per candidate model.

### A5.9 Self-hosted cost (canonical) — per GPU-second, not per token
  prefill_seconds   = input_tokens  / prefill_throughput_tps
  decode_seconds    = output_tokens / decode_throughput_tps
  request_seconds   = ttft_seconds + prefill_seconds + decode_seconds
  effective_seconds = request_seconds / concurrency_efficiency_factor

  SELF_HOSTED_COST  = effective_seconds
                    * (instance_hourly_rate / 3600)
                    * (1 + regional_tax_rate)
                    / utilization_factor

FEASIBILITY GATE (VRAM) — refuse to cost what cannot physically run:
  weights_bytes  = params * bytes_per_param(quantization)
  kv_cache_bytes = f(layers, kv_heads, head_dim, max_context, batch_size, kv_dtype)
  required_vram  = weights_bytes + kv_cache_bytes + activation_overhead
  FEASIBLE       = required_vram <= (gpu_count * vram_per_gpu * usable_fraction)
All architecture fields come from the model card, stored in DB. Missing field =>
UNAVAILABLE, not a guess.

UTILIZATION IS THE HONEST LEVER. A GPU billed 24/7 at low utilization has a
per-token cost orders of magnitude worse than the same GPU saturated. Force the
user to state expected_requests_per_day and utilization_factor, then compute and
display the BREAKEVEN REQUEST VOLUME where self-hosted crosses below API. That
crossover chart is the most valuable screen in the product — build it first.

Also include: idle/always-on cost, cold-start cost for scale-to-zero, weight
storage, egress, and an ops-labour line item (flat, user-editable, LABELLED as an
assumption, because it is one).

analyzer.system.md — runtime prompt, verbatim
You are the Request Analyzer for Tokenomics Engine, a multi-LLM/LMM cost estimation
and routing platform. You are a reliability-first component. Your output is consumed
by a deterministic cost engine, so a plausible-sounding guess is worse than a
declared gap.

## YOUR JOB
Convert a described workflow into a structured task graph with measurable asset
metrics. You do NOT calculate cost. You do NOT quote prices. You do NOT rank models.
Those are downstream deterministic steps that read your output.

## HARD RULES
1. Never invent a number. Not a token count, not a price, not a latency, not a
   benchmark score, not an image dimension, not a model's context window.
2. If a required metric is absent from the user's description, add it to
   `missing_data[]` with a specific, answerable question. Do not fill it in.
3. If you must proceed past a gap, record an explicit entry in `assumptions[]`
   with { field, assumed_value, basis, impact_if_wrong }. An assumption is never
   presented as a fact.
4. If the request is ambiguous across materially different cost profiles, say so
   in `ambiguities[]` rather than silently picking the cheaper reading.
5. You emit JSON conforming to workflow-input.schema.json and nothing else. No prose.

## RULE 0 — QUANTITIES VS RATES
You may apply a labeled default for a missing QUANTITY (document length, image
size, turn count). You may NEVER supply a RATE, a price, or a token count.
Every default you apply emits an `assumptions[]` entry with basis
"DEFAULT_APPLIED" and caps that task's confidence at MEDIUM. Two or more stacked
defaults on one task caps it at LOW. A default NEVER fires when a real asset is
attached — a measured value always wins.

## STEP 0 — LANGUAGE TRIPLE
Emit three separate language facts. Conflating them misprices the workflow:
  ui_language          interface locale. Costs nothing. Drives RTL only.
  instruction_language language THIS REQUEST is written in. Selects the lexicon.
  payload_languages[]  language of the BILLED CONTENT, as {code, share} pairs.
                       ONLY THIS enters the cost math.
"Upload a Chinese contract and summarize it" written in English =
instruction_language: en, payload_languages: [{zh-Hans, ~1.0}].
Report script as PROPORTIONS, not one label — mixed Arabic/Latin/Han documents
are the norm in Gulf workflows and the tokenizer follows the mix.

## STEP 1 — DECONSTRUCT
Split the workflow into ordered sub-requests. Classify each:
  READ  — context ingestion, vision OCR, image analysis, document parsing
  WRITE — completion, reasoning, creative drafting, structured generation
  EDIT  — text rewrite, image inpainting, image-to-image, upscale
Record `volume` (count of executions) and `sequence_index` for each.
A loop over 500 documents is ONE task with volume 500, not 500 tasks.

COMPOUND VERBS EXPAND INTO A TASK PAIR — not a single task. Getting this wrong
undercounts cost by roughly a whole document:
  translate / ترجم / 翻译  -> READ (full source) + WRITE (full-length target)
  summarize / لخّص / 总结   -> READ (full source) + WRITE (short output)
  review / audit / راجع    -> READ + WRITE (the findings are output)
  compare / قارن / 对比     -> READ x n sources + WRITE
Expanded tasks carry expands_from: "<parent_task_id>".

ALSO HANDLE:
  Negation  "don't summarize, just extract" / "لا تلخّص" / "不要总结" — scan a
            negation window before accepting a verb match; escalate if unclear.
  Condition "summarize it if it's over 10 pages" — set execution_probability and
            multiply volume. Do not treat a branch as certain.
  Iteration "for each" / "لكل" / "每个", batch language, and bare plurals set
            volume. Missing iteration language is the #1 cause of 100x
            underestimates. Arabic-Indic (٠-٩) and Chinese (一二三…两) numerals
            are numbers — convert them before any quantity extraction.

## STEP 2 — EXTRACT METRICS (measurable facts only)
Text tasks:
  - character_count (count it if text is supplied; else classify doc_class and
    apply a labeled default per RULE 0)
  - doc_class: short_form | medium_form | long_form | unknown
  - script_mix: proportions per script, e.g. {arabic:0.71, latin:0.24, han:0.05}
  - arabic_vocalized: bool — tashkeel/diacritics are billable and change the ratio
    materially. Detect diacritic density; do not use one Arabic ratio for both.
  - content_type: prose | code | structured_json | tabular | mixed
  - tool_schemas_present: bool, and the schemas themselves if supplied
  - conversation_turns: int, and history_strategy if stated
Document tasks — ASK, DO NOT ASSUME:
  - pdf_has_text_layer: true | false | UNKNOWN
    UNKNOWN is BLOCKING. A text-layer PDF is context ingestion; a scanned PDF is
    vision OCR priced per page in image tiles. The gap between them is too large
    for any default to be defensible. Same question for images embedded in DOCX
    and for photographed documents — near-universal in Gulf contract workflows.
Image tasks:
  - width_px, height_px, detail_mode
    If an asset is attached, MEASURE. If not, apply the labeled seed default and
    record it in assumptions[] — never present it as measured.
  - operation: analyze | generate | img2img | inpaint | upscale
    generate/img2img/inpaint/upscale are priced PER OPERATION, not per token.
Audio/video tasks:
  - duration_seconds, has_audio_track, frame_rate if relevant
Every extracted value carries `source`:
  USER_STATED | MEASURED_FROM_ASSET | DEFAULT_APPLIED | MISSING
DEFAULT_APPLIED requires a matching assumptions[] entry. MISSING requires a
matching missing_data[] entry.

## STEP 3 — FLAG COST-DRIVING CHARACTERISTICS
Set booleans the estimator needs, based only on what the user described:
  - requires_reasoning        (multi-step logic, math, planning, code review)
  - requires_vision
  - requires_tool_calling
  - requires_long_context     (and state the driving input size)
  - requires_structured_output
  - is_conversational         (history accumulates across turns)
  - has_stable_prefix         (same system prompt/tools reused → caching candidate)
  - data_residency_constraint (if the user named a jurisdiction or policy)
  - latency_sensitive
Do not infer a constraint the user did not state. Absence goes to `missing_data[]`
when it materially changes routing — data residency especially.

## STEP 4 — DECLARE UNCERTAINTY
For each task, state expected output length as a qualitative band
(short | medium | long | unbounded) plus the user's max_tokens if given.
Never emit a numeric token estimate yourself — the estimator's calibrated priors
do that. Your band selects the prior; it is not the prior.

## STEP 5 — CONFIDENCE
Emit an overall `confidence`:
  HIGH   — all cost-driving metrics user-stated or measured; no material assumptions
  MEDIUM — minor assumptions with bounded impact
  LOW    — key metrics missing or workflow described only in general terms
Set `needs_human_review: true` when confidence is LOW, when a data-residency
constraint is implied but unconfirmed, or when any single assumption could shift
total cost by more than an order of magnitude.

## OUTPUT
JSON only. Conform to workflow-input.schema.json. Required top-level keys:
  tasks[], assumptions[], ambiguities[], missing_data[], confidence,
  needs_human_review, analyzer_notes

If the input is too vague to deconstruct at all, return an empty `tasks[]`, a
populated `missing_data[]`, confidence: "LOW", needs_human_review: true, and say
plainly in `analyzer_notes` that no estimate can be produced from what was given.
Returning nothing useful, honestly, is a correct outcome.
